# Bug Hunt 2026 security review

Repository layout note: historical `app/` paths in this audit now correspond to `frontend/`; canonical SQL migrations are in `backend/supabase/migrations/`. The findings describe the original tested deployment.

Reviewed on 9 October 2026 (Asia/Karachi), against deployed source commit `b8605b32bbb63e929715ceedc84cf3f7cd509c9d` and the live Supabase project. Website: https://bughunt-2026-arena.snappyhippo4.chatgpt.site.

The main findings are missing enforced staff MFA, missing general application API rate limits, browser-readable persisted authentication tokens, missing deployed security headers, and vulnerable development dependencies. No exploitable SQL injection, XSS, cross-team object access, or anonymous mutation was demonstrated in the checks performed. This is a bounded source/configuration review with targeted tests, not a comprehensive penetration test or a guarantee that other vulnerabilities do not exist.

The review used read-only live database queries, public authentication metadata, a small number of rejected authorization probes, owner-authorized website requests, isolated PostgreSQL tests, and browser tests with synthetic intercepted authentication/data responses. No live event records, account passwords, permissions, or deployment settings were changed. Credentials, password hashes, and real authentication tokens are absent from this report. Audit helpers are in the original workspace's ignored `tools/`; sanitized detailed evidence is in ignored `private/security-*-evidence.json` and `private/security-evidence.json`.

| # | Requested check | Result and evidence |
| --- | --- | --- |
| 1 | SQL injection | **No issue demonstrated.** Application RPCs use typed arguments and static SQL. Dynamic SQL in migrations operates on operator-controlled object names. Injection-shaped registration and answer values remained literal data in isolated PostgreSQL; an injection-shaped staff selector did not reach private keys. The operator seed/provisioning script escapes string literals; its SQL migration files already require privileged operator trust. |
| 2 | XSS | **No executable XSS demonstrated; defense missing.** React renders participant names, answers, announcements, and review text as text. In the deployed browser, injected image/event-handler announcement and SVG/event-handler team-name strings remained text; no injected elements or payload execution occurred. The unused starter chart component has a raw CSS HTML sink: do not supply it untrusted configuration if it is introduced into the product. Live HTML has no Content-Security-Policy, described below. |
| 3 | CSRF | **No protected API CSRF demonstrated.** Supabase mutations require an explicit bearer token; the application does not authenticate its database mutations through automatically attached browser cookies. A cross-origin unauthenticated admin mutation returned HTTP 401. Anonymous form-shaped operations and protected RPCs were denied in isolated tests. The managed Sites access gate has its own cookie/session boundary and was not comprehensively tested. Any future cookie-authenticated backend needs Origin validation and CSRF protection. |
| 4 | Insecure file uploads | **Not applicable to current product.** No upload workflow or upload endpoint is connected, and the live project has zero Storage buckets. A generic unused attachment UI component is not an upload service. Reassess server-side type/size checks, authorization, storage policies, and malware handling if uploads are added. |
| 5 | IDOR / broken object authorization | **No issue demonstrated.** Team IDs derive from the verified user's ownership, rather than a caller-supplied team ID. Team B could not retrieve Team A's drafts/submissions, access private tables, modify ownership, grade submissions, or review arbitrary claims. Judges could not invoke admin actions. Certificate UUID verification intentionally exposes limited public certificate fields. |
| 6 | Missing rate limiting | **High-priority gap.** There is no general per-user/per-IP request limiter for application RPC reads, heartbeat, drafts, or most writes; anonymous public-state/certificate requests have no application limiter. Clarifications have a 15-second cooldown and a 50-item cap; claims, activities, and answer attempts have item quotas. Those do not bound request frequency. Supabase Auth has provider-level authentication limits, but the project's exact limits, CAPTCHA, and upstream abuse protections were not verified through a management credential. [Supabase Auth rate limits](https://supabase.com/docs/guides/auth/rate-limits) apply to authentication endpoints, not a substitute for application RPC limits. |
| 7 | Insecure JWT secrets | **No weakness observed in active published signing key; partial configuration coverage.** Live JWKS advertises ES256 / P-256, and an unsigned `alg:none` token was rejected with HTTP 401. No custom JWT secret or homegrown signature verifier is used by the application. Private signing-key entropy, key rotation, legacy HS256 acceptance, and full token-lifetime settings were not audited. JWKS contains public verification keys, not secrets. See [Supabase JWT verification](https://supabase.com/docs/guides/auth/jwts). |
| 8 | Exposed API secrets | **No leak found in reviewed surfaces.** The source/build credential scan passed; the one source Git commit had zero matches for the actual service key or database password. Owner-authorized requests for `/.env`, `/.env.local`, and `/.git/config` returned 404. Browser configuration contains only URL/publishable key, as intended by [Supabase API-key guidance](https://supabase.com/docs/guides/getting-started/api-keys). This does not assess unrelated external repositories, backups, or prior credentials. |
| 9 | Weak password hashing | **No weak hashing observed.** Aggregate database inspection found the two existing password records use bcrypt with cost 10; no hash values were printed. The application delegates hashing to Supabase Auth and does not store plaintext passwords. This is separate from password strength: minimum length, compromised-password rejection, and password-policy configuration still need dashboard verification. [Supabase password security](https://supabase.com/docs/guides/auth/password-security) describes the provider controls. |
| 10 | Missing MFA | **High-priority gap.** The one current staff account has zero verified MFA factors. There is no MFA enrollment/challenge UI, and `bughunt.require_staff()` checks the staff role without enforcing JWT `aal = aal2`. A stolen staff password can therefore authorize privileged scoring/event operations. Implement both enrollment/challenge and database enforcement; a frontend-only MFA prompt is insufficient. See [Supabase MFA](https://supabase.com/docs/guides/auth/auth-mfa). |
| 11 | Overly permissive CORS | **Broad provider CORS; no authorization bypass demonstrated.** Supabase accepted the foreign-origin preflight with `Access-Control-Allow-Origin: *`, allowed Authorization/API-key headers, and did not return `Access-Control-Allow-Credentials: true`. The cross-origin unauthenticated mutation was still rejected. This is compatible with a browser bearer-token API; broad CORS alone is not an IDOR or CSRF exploit. CORS does not block direct scripts/curl. An origin-restricted gateway only becomes a meaningful sole entry point if direct protected RPC access is also addressed. |
| 12 | Auth tokens in local storage | **Confirmed risk, medium priority; greater impact for staff.** `persistSession: true` uses Supabase's default browser storage. The synthetic login browser test confirmed both access and refresh tokens in local storage without recording their values. Any same-origin script execution can steal them; tokens also persist on a shared device. A server session/BFF with HttpOnly, Secure, appropriately SameSite cookies is the preferred redesign for protecting tokens from JavaScript, together with CSRF controls. Session storage only reduces persistence; it does not solve XSS token theft. |
| 13 | Client-only permission enforcement | **No issue demonstrated.** UI visibility is backed by database authorization. `require_user()` checks the JWT subject/session against `auth.sessions`; `require_staff()` checks protected staff records; `require_team()` checks ownership and an active competition lease. Spoofed frontend role choices do not grant server permission. All 28 privileged functions inspected have an explicitly fixed empty search path. |
| 14 | Missing RLS | **Verified present.** All 23 application tables in the live database have RLS and explicit policies. All 22 private-schema tables deny direct anonymous/authenticated access, and both roles lack private-schema USAGE. The public control-signal table deliberately allows timestamp-only SELECT; writes are denied. Security-definer RPCs bypass owner RLS by design, so their authorization checks remain essential. |
| 15 | Unverified webhook signatures | **Not applicable to current application.** There is no connected webhook handler. Supabase-managed email/auth flows are not application webhook receivers. Require provider signature verification over the raw body and replay protections before adding a webhook endpoint. |
| 16 | SSRF | **No reachable application SSRF sink found.** The deployed application is a static export with no custom server endpoint that fetches caller-supplied URLs. Browser API destinations are configured Supabase URLs. Retained connector/worker preview code is not the deployed runtime. Reassess redirects, DNS/private-address restrictions, and destination allowlists if server-side remote fetching is introduced. |
| 17 | Exposed source maps | **No exposure found in tested assets.** No `.map` files were present in `app/out`. All nine JavaScript assets loaded by the deployed entry page lacked source-map directives; their `.map` URLs returned 404. This does not certify every provider/internal build artifact or future lazy route. |
| 18 | Default credentials | **None found in production setup.** Admin provisioning reserves a verified email and does not create a password. Test scripts contain clearly isolated synthetic credentials/Auth transport; these are not provisioned live accounts. This review did not perform password guessing or login attempts against real accounts. |
| 19 | Sensitive logs | **Partial: no credential leaks found; sensitive audit records exist.** The one local log scanned had no actual service-key/password match; product components do not explicitly log passwords/tokens. Database audit rows intentionally retain previous team/review records, which can include member PII and submitted answers. These are private, but need documented retention, limited staff access, and minimization. Supabase Auth/API/provider logs and their retention were not reviewed, so a blanket “no sensitive data in logs” claim would be unsupported. |
| 20 | Vulnerable dependencies | **Development findings remain.** Fresh `npm audit --omit=dev` reports zero known findings. The full audit reports 20 affected packages: 13 high, 7 moderate, zero critical. These are development/lint/starter tooling, including braces/micromatch, esbuild, image-size, React Server DOM, undici, Vite, and ws dependency chains. They are not included as a server runtime in the static deployment. Do not expose development servers. Patch compatible upstream versions and verify the tooling; a blind forced audit fix proposes incompatible replacements, including downgrades. Zero reported production findings is not proof that every dependency is safe. |

The deployed HTML's actual response headers do not include CSP, HSTS, X-Content-Type-Options, Referrer-Policy, or Permissions-Policy. `app/public/_headers` specifies them but is served as a static file at `/_headers` instead of being interpreted by this host. The original local/header-file configuration therefore does not protect the deployed page. This is a confirmed deployment hardening gap, not a demonstrated XSS exploit. Apply headers through supported hosting response configuration or a worker serving the static assets. Prefer script hashes/nonces over the file's current `script-src 'unsafe-inline'`; preserve the app's Supabase connection and intended framing requirements. HSTS needs an HTTP response header; a CSP meta tag cannot replace all response-header controls.

Recommended work, in priority order:

1. Require MFA for administrators and judges. Provide tested enrollment/challenge and recovery procedures, then enforce `aal2` in the database before enabling the restriction. Avoid locking out staff through a database-only change.
2. Add bounded, atomic per-user request budgets for application RPCs and an appropriate gateway/WAF policy for anonymous abuse. Include a legitimate 500-team workload test and limiter tests. Count read requests as well as mutations, allow realistic autosave/reconnect bursts, and ensure alternate direct entry points cannot bypass the chosen limit.
3. Apply and verify real production security headers. Test the deployed header values and confirm that legitimate authentication, realtime updates, printing, and embedded access still work.
4. Redesign authentication persistence if HttpOnly token protection is required. A cookie backend needs corresponding CSRF protection and server-side authorization; copying tokens to a JavaScript-readable cookie is not a fix.
5. Update and verify affected development tooling. Review provider password controls, CAPTCHA/rate-limit settings, legacy signing keys, secret rotation, and log retention in the management dashboard.

The managed website is currently owner-private (one explicitly allowed viewer, no groups). This restricts page access; it does not put the separate Supabase API behind that same Sites access gate. Database authorization must continue to protect that API directly.

Evidence summary: 11/11 targeted isolated security checks passed; live table/function grant review covered 23 tables and 29 functions; forged JWT and cross-origin anonymous admin requests returned 401; private REST table lookup returned 404; synthetic deployed-browser XSS checks passed with zero browser exceptions; persisted access/refresh tokens were confirmed; nine source-map URL checks returned 404; one Git commit and one local log had zero matches for configured private credentials. No changes to production were made during this review.
